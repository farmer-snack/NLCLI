[2026-11-16] 定制点 / 集控与管理链路的延时是故意设计，不是 bug
现象：管理/集控/档案同步链路里有多处几秒级等待，审查时极易被判成性能缺陷或死等。
根因：上游故意留出的时间窗，等管理端把数据拉走；删掉会让集控功能失效或丢数据。
结论：管理链路（ManagementService、集控、档案同步、Ipc）里的延时/超时/重试参数一律不动。「看着慢」不是证据，必须能给出确定性复现路径才算缺陷。

[2026-11-16] 流程 / 修 bug 前必须先排除「这是故意留的」
现象：上一轮把若干行为当缺陷修掉，其中一部分可能本就是上游有意为之。
根因：只按「代码不优雅 / 有等待 / 吞了异常 / 没判空」判断，缺少反证步骤。
结论：动手前三问——(1) 代码或提交信息有没有说明意图；(2) 删掉会不会让某个功能失去时间窗或兜底；(3) 能否确定性复现。三问都不成立才动手，否则只记录不修。

[2026-11-16] 环境 / git 仓库根是 nlcli/，不是 nlcli/ClassIsland/
现象：在 nlcli/ClassIsland 下执行 `git log -- <path>` 静默返回空，误判文件未被跟踪。
根因：仓库根在 nlcli/，ClassIsland 只是子目录；相对路径被当成额外前缀。
结论：任何路径历史查询前先 `git rev-parse --show-toplevel` 确认根，再从根拼路径。

[2026-11-16] 合并 / 用 rebase --onto 丢弃中间提交，账本文件必冲突
现象：丢弃 f456d257 后重放后续提交，ff0caa44 与 87eca09c 在 fixxed.txt 上连续冲突。
根因：后续提交的账本 diff 夹带了被丢提交的上下文；87eca09c 还整体重排过账本。
结论：遇到整文件重排型冲突，不要手工合并——直接 `git show <该提交>:fixxed.txt` 取后续版本，再用脚本剥离被丢提交的内容，最后替换工作区文件。

[2026-11-16] 合并 / 补丁里的 `Subproject commit` 来自 gitlink 变化
现象：format-patch 产出中出现 `-Subproject commit ...` 一行。
根因：子模块目录在 git 里只是一个 gitlink（mode 160000），转成实体文件或反之都表现为这一行。
结论：判据必须用行首精确匹配 `grep -cE "^[-+]Subproject commit" update.txt`；直接 `grep -c "Subproject commit"` 会被 memory.txt、注释里的说明文字自身命中，得出假阳性。`git diff --stat <base>..HEAD -- vendors/EdgeTtsSharp` 为空可交叉验证。

[2026-11-16] 流程 / 审计结论必须落盘，压缩后只剩文件
现象：14 路审计代理的报告在上下文压缩后全部丢失，无法复核。
根因：报告只存在于对话里，压缩即蒸发。
结论：多路审计一律要求写进 audit/NN-xxx.md（编号+主题），并在 RULES.md 里统一只读约束；后续只读文件复核，不依赖对话记忆。

[2026-11-16] 流程 / 自己上一轮的修复方案也要当成可疑对象
现象：上一轮为修并发问题加的 `_pendingRescheduleCount` 全局闸门，本身造成「任一条提醒移交就冻结所有派发 5 秒」。
根因：用全局锁解决局部竞争，把隔离性换成了串行性。
结论：并发修复优先「按票据/按对象隔离」，禁止用全局计数器或全局布尔做闸门；改完要反问「这个锁会不会误伤无关请求」。

[2026-11-16] 流程 / 判断「是否默认值」必须先读字段初始化
现象：CronTrigger 守卫写成 `DebugTimeSpeed != 0`，而该字段默认 1.0，导致默认配置下永不重建 worker。
根因：凭「0 是默认」的直觉写判断，没核对字段初始化表达式。
结论：任何 default-value 守卫，先 grep 字段声明处的初始值，再写条件；写完用默认配置走一遍分支。

[2026-11-16] 环境 / FileBin 上传端点是 POST /{bin}/{filename}
现象：`POST /{bin}` 配 `filename` 头返回 405/400。
根因：FileBin 传文件走路径里的文件名，不是请求头。
结论：`curl -X POST --data-binary @file "https://filebin.net/<bin>/<filename>"`；同名会覆盖旧文件，需要保留旧版就换文件名传到同一个 bin。校验用 `/sha256/<bin>`。

[2026-11-16] 构建 / 编译验证看「0 Error(s)」，警告数是上游固有
现象：Release 构建输出 1300+ 条警告，全部为上游已有的 Avalonia 绑定/可空性警告。
根因：上游代码本身带这些警告，与本地定制无关。
结论：判据是 `0 Error(s)` 且退出码 0；警告数不作为回归指标，除非出现新的 CSxxxx 且指向本轮改动的文件。

[2026-11-16] 构建 / Android 缺 workload，只能靠守卫保兼容
现象：本机无 Android workload，`dotnet build` 无法验证 Android 目标。
根因：未安装 net10.0-android 工作负载。
结论：新增代码只用跨平台 API；平台相关一律 `OperatingSystem.IsWindows()` 等守卫包裹，并在 WPF/Win32 P/Invoke 处加 `[SupportedOSPlatform]` 或运行时判断，保证其它平台只是不启用而非崩溃。
