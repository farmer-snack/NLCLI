[长期] 主界面宽度与提醒排版稳定
================================================

需求（2026-10-29 起，多轮迭代到 2026-11-13）：
提醒播放期间主界面不能变宽变窄；轮播容器切换内容不能带动整行宽度；
所有提醒按自己的文字长度定宽，播放期间只增不减、文字不被压扁。

这是一条链上的三个层次，缺任何一层都会复发，按层说明。

1）面板层（Rectangles 主题的气泡）
- RectanglesNotificationPanel：宽度规则从「弹出后 600ms 内允许增长」改为
  「整个播放期间只增不减」——内容变长时跟上，变短时保持不变。
- 宽度比较加 0.5px 容差，候选宽度向上取整到整像素，动画重启阈值同步放宽，
  避免亚像素抖动反复重启 333ms 宽度动画（表现得像气泡持续抽动）。
- RectanglesNotificationBubble.MeasureContentWidth：测量内容自然宽度时，
  把轮播容器（ListBox 等）里所有已生成的项都算进来取最大值。
- 宽度上限仍是窗口宽度的 80%，超长内容在该上限内裁切/省略。

2）模板部件层（内嵌式主题：Fluent / LiquidGlass / Classic）
- 三套模板里 GridOverlay / GridContentRoot 是 PART_GridWrapper 的并列子元素，
  遮罩、叠加内容参与父 Grid 测量，内容比主界面组件宽时就把整条岛撑开。
  只改面板层对内嵌式主题完全无效，必须在这一层锁。
- MainWindowLine 新增 LockRowWidth / UnlockRowWidth：提醒开始播放前记下
  PART_GridWrapper 的实际宽度并写死，播放结束恢复 NaN 自适应；锁定期间
  WrapperOnSizeChanged 不再回写 BackgroundWidth，内容改为溢出显示。
- 锁定前先 TopLevel.UpdateLayout() 强制排一遍布局，避免「整行组件都被隐藏、
  提醒开始时行才出现、Bounds 仍为 0」导致锁定被跳过。
- 模板重建（切主题、换外观）会在 OnApplyTemplate 里换掉 GridWrapper 实例。旧实例上的
  Width 限制随旧模板一起消失，但锁标志还是 true —— 必须把 _lockedRowWidth 迁移到新实例，
  否则 WrapperOnSizeChanged 会一直直接 return，BackgroundWidth 再也不更新，背景宽度卡死在旧值。
  未处于锁定状态时则顺手清空锁标志与锁宽度，避免上一个模板的残留值影响下一次。

3）组件层（轮播容器）
- SlideComponent 的 ListBox 用 Grid 做 ItemsPanel，所有轮播项叠在同一格里。
  未选中项原本用 IsVisible=False 隐藏，而 Avalonia 中不可见元素不参与测量，
  于是 ListBox 的测量宽度只等于当前显示项——切一次轮播整行宽度变一次。
- 改为 Opacity=0 + IsHitTestVisible=False 隐藏未选中项、选中项 ZIndex=1 置顶，
  所有项都参与测量，轮播宽度恒为最宽项；滑动动画同步从 IsVisible 改 Opacity 驱动。

4）异常穿透与面板复用（审计补充）
- ProcessNotification 是 async void，原来整段只 catch (TaskCanceledException)。
  其它异常（内容绑定/模板出错、GetCenter 拿不到窗口）会直接穿透 async void 终止方法：
  _isOverlayOpen 永远停在 true，后续提醒全被挡在门外；UnlockRowWidth 不执行，行宽永久锁死。
  改为整段 try/catch/finally —— 单条提醒加通用 catch，记日志后跳过继续下一条；
  finally 统一清 OverlayContent / MaskContent、复位 _isOverlayOpen、解锁行宽、释放 Topmost 锁。
  finally 里的 CancelAsync / Dispose 再包一层 try/catch，收尾自身抛异常也不能让 Topmost 锁漏释放。
- 面板宽度锁「播放期间只增不减」的前提是「一次播放一个面板」，但 RectanglesNotificationPanel
  实例会在多条提醒之间复用。同一 IsOpened 周期内只换 MaskContent 不会重置 _lockedWidth，
  上一条宽提醒的宽度会一直沿用到下一条短提醒，表现的正是「短提醒被撑宽」。
  新增 ResetWidthLock() 清 _lockedWidth，MainWindowLine 在给 MaskContent 赋值之后调用；
  其他主题没有这个面板，GetVisualParent 找不到时直接跳过。

- ClassIsland/Controls/RectanglesNotificationPanel.cs — 只增不减 + 0.5px 容差
- ClassIsland/Controls/RectanglesNotificationBubble.cs — 纳入轮播容器所有项
- ClassIsland/Controls/Components/SlideComponent.axaml — Opacity 隐藏 + ZIndex

追加（2026-11-14）
--------
- 提醒队列的泄漏与上限（审计补充）
  * PoppedRequests 只在「票据被取消」时移除；正常播完走的是 CompletedToken 回调，
    只清 PlayingTickets，PoppedRequests 里的记录永久残留。同一条请求再次入队会被
    PopRequests 当成「已弹出」直接丢弃，长时间运行还会持续占内存。
    → CompletedToken 回调里一并 Remove。
  * CancelAllNotifications 只从队列 Dequeue，不清理 EnqueuedRequests，这些请求之后
    Add 永远返回 false、再也无法重新入队。→ 出队时同步 Remove。
  * RequestQueue 没有上限，上游高频推送（cron 被反复重建）时无限积压。
    → 上限 256，超限丢弃新请求并 Cancel 其 CompletedToken，避免调用方 await 永久挂起。
  * NotificationPriority 的插队比较违反反对称性（两个插队项互相返回 1），且最小堆下
    普通项反而排在插队项前面。→ 只在插队状态不同时返回 -1/1。

补充（2026-11-14 二次审计：提醒重排链路）
--------
- 撤掉全局派发闸门。上一轮用 _pendingRescheduleCount 拦住所有派发、等票据收尾后再重排，
  它有三个问题：① 全局计数，任意一条提醒移交/卸载期间所有新提醒最长 5 秒派发不出去；
  ② 超时分支直接丢弃提醒；③ 收尾信号本身存在「永不完成」的路径（见下），闸门会长期为真。
  → 改成按票据异步重排：取消回调只做同步清理，收尾等待放在独立 Task 里，不影响别的提醒；
  超时则把请求标记为已结束并放行 CompletedToken，避免自动化行动永久挂起。
- 取消回调是 async void，原 try 只包住 await，前置的集合修改、UpdateNotificationPlayingState、
  重排入队全在 try 外，异常会经 Cancel() 抛给调用方（窗口卸载）或成为未观察异常。
  → 整段收口；宿主集合与 IsNotificationsPlaying 统一 marshal 到 UI 线程（插件可从后台线程
  调 ShowNotification，裸集合会被并发修改）。
- 票据收尾信号必须无条件完成：ProcessNotificationSessionCore 的 finally 里
  await soundsCts.CancelAsync() 一旦抛异常就跳过 TrySetResult，宿主永远等不到。
  → 收尾整体兜底，TrySetResult 放到最外层 finally；遮罩正常结束但正文因时长为 0 被跳过时
  也要给出信号（延迟兜底）。
- PopRequests 用破坏性的 PoppedRequests.Remove(head) 判重：do-while 在同一轮里会多次检查
  同一个链头，第一次 Remove 返回 true 并删掉记录，第二次返回 false，于是把已投递过的整条链
  再投一遍 —— 链式提醒的链尾被播放两次。→ 只读 Contains 判重，跳过已有活跃票据的请求，
  并删掉不可达的 `if (headPopped) return []`。
- 先建票再判断消费者会留下永远不会播放的孤儿票据（一请求两票据）。→ 先确认有消费者再接单；
  消费者抛异常时回滚 PlayingNotifications 并返回失败。
- 外层 catch 丢弃当前票据时漏了状态转移与 CompletedToken：当前票据已出队、不在队列里，
  外层 catch 引用不到它，宿主集合永久残留；队列里被 Cancel 的票据则会被宿主当成
  「被移交」重新入队，过一会儿又弹出来。→ 用 currentTicket 跟踪当前票据，
  统一走 DiscardNotificationTicket（先 State/CompletedToken，再 Cancel）。
- RectanglesNotificationPanel.AnimateRevealProgress 的 setup（预留窗口渲染尺寸、
  抑制后续行动画）原本在 try 之外，任一步抛异常都不会走恢复分支：窗口尺寸被永久锁死、
  后续行的位移动画永久失效。→ setup 移入 try，异常路径同步归还租约；
  ReserveWindowRenderSize 内部失败也会把已写入的尺寸租约还回去。

[长期] 插件兼容层（旧版 Avalonia 插件在新宿主加载）
================================================

需求（2026-10-29 起，多轮迭代到 2026-11-09）：
插件市场里所有 2.x 插件（含按 Avalonia 11 / FluentAvalonia 2 编译的）都要能直接加载；
同为 Avalonia 12 编译的插件原样加载、不做任何改写。判定不能针对插件名做特判。

核心机制：ClassIsland/Services/PluginCompatibility/PluginTypeCompatibility.cs
- 加载前用 Mono.Cecil 重写插件程序集的类型引用。判定只有一条：
  插件引用的 Avalonia 主版本 < 宿主主版本（11 → 12）才改写；同主版本直接跳过。
- 映射表由宿主发布目录的实际类型表推导（PEReader 扫全部 dll），不含插件名特判：
  · 规则 A：类型换到宿主里的另一个程序集（Avalonia.Markup → Avalonia.Base 等）；
  · 规则 A2：独立类型被收进外层类型（DrawerPlacementEnum → DrawerHost/DrawerPlacementEnum），
    按「简单名唯一 + 命名空间同源」推断；
  · 规则 B：FluentAvalonia 3 给控件统一加 FA 前缀（ContentDialog → FAContentDialog 等）；
  · 规则 C：宿主自身 API 的命名空间迁移（同名类型唯一时才生效）；
  · 嵌套类型的全名（Outer/Inner）也进索引，避免合法嵌套引用被误判成缺失。
- 改写结果按「源文件 SHA256 + 宿主主版本」缓存，插件或宿主更新自动失效；
  任何异常都退回原文件加载，不会因为兼容层本身让插件更糟。

已经被上游改掉、必须一直垫着的兼容映射
--------------------------------------
- SystemDecorations → WindowDecorations：Avalonia 12 把 Window.SystemDecorations 改名。
  RemovedTypeAliases 的四元组必须带 IsValueType 标志，NormalizeType 改名时同步写入。
  漏设会被写成 class 签名，JIT 解析失败报 Method not found（数值一致：None=0/BorderOnly=1/Full=2）。
- GotFocusEventArgs 在 12 里被删除 → 别名到 FocusChangedEventArgs。
- InputElement.LostFocus / GotFocus 事件参数从 RoutedEventArgs 改成 FocusChangedEventArgs，
  插件用 add_LostFocus(EventHandler<RoutedEventArgs>) 订阅会报 MissingMethodException。
  → 事件访问器 add_/remove_ 重定向到 Avalonia12Compatibility.AddLostFocus / RemoveLostFocus，
    用 ConditionalWeakTable 保存包装委托，把旧签名适配到新签名。
- IClipboard.GetTextAsync / SetTextAsync、IDataTransfer、DragDrop.DoDragDrop、
  ToggleButton.CheckedEvent、Binding(string, BindingMode) 属于 Avalonia 12 真实 API 破坏，
  改名解决不了；其中已用垫片覆盖的见 Avalonia12Compatibility，其余仍会在插件侧报缺失。

加载上下文（ClassIsland/PluginLoadContext.cs）
- 插件包自带的 ClassIsland.* / Avalonia* 一律绑定宿主已加载实例，忽略插件要求的版本号
  与包内副本——否则 PluginBase、组件基类会类型分裂，插件显示「已加载」但组件一个都不出现。
- 无 deps.json 时按「插件目录下同名 dll」兜底加载，入口程序集也走这条路；
  插件没打包的框架类库复用宿主已加载的同名程序集。
- 原生库按平台命名约定在插件目录、runtimes/<平台>/native、runtimes/<平台>-<架构>/native 查找
  （Windows .dll，Linux lib*.so / *.so，macOS lib*.dylib / *.dylib）。

PluginService 与可观测性
- ApiVersion 校验改为 CheckApiVersionCompatibility：低于 2.0.0.0 仍拒绝（1.x WPF 运行时
  完全不兼容）；高于当前版本不再阻止，只提示；没写或写错放行；"2.0" 这种省略段位不再被误判。
- 加载失败改为 BuildLoadException：包成中文说明（缺依赖 / 类型方法缺失 / 32 位插件跑 64 位进程），
  完整异常链打日志。
- 插件详情页：状态徽章旁「兼容层已介入」徽章，悬停显示调整过哪些程序集；
  新增 CompatibilityNotes / HasCompatibilityNotes / AddCompatibilityNote（内部切 UI 线程）。

插件市场
- PluginMarketService：索引、图标、README 首次访问成功后落盘缓存到

- 市场列表项与详情页显示「原生支持 / 需要兼容层」标签，插件页 OnLoaded 触发探测。

补充（2026-11-20：FluentAvalonia Expander 展开动画空引用）
--------

（TraceID 04e11f83…，堆栈 FluentAvalonia.UI.Controls.FAExpanderExt.ExpanderInfo.HandleExpanderTemplateApplied）。
- 根因（已反编译 FluentAvaloniaUI 3.0.0/3.0.1/3.0.2/3.1.0 的 dll 逐版本确认，四个版本方法 IL 完全一致）：

- 修法：App_OnDispatcherUnhandledException 开头新增 IsFluentAvaloniaExpanderAnimationException 精准判定
  （必须同时是 NullReferenceException 且堆栈含 FAExpanderExt + HandleExpanderTemplateApplied，
  并沿 InnerException 向内展开），命中则记 warning 日志后 e.Handled=true 直接返回，不进崩溃流程。
  条件刻意收窄，真正的其它空引用仍照常上报；仅隔离这一次无害的动画异常。
- 为什么不动依赖：升级 FluentAvaloniaUI 到 3.1.0 无法规避（该方法 IL 与 3.0.0 相同，均未判空）。
- 涉及文件：ClassIsland/App.axaml.cs（App_OnDispatcherUnhandledException + 新增判定方法）。

补充（子代理审计：IL 改写计数自洽）
- PluginTypeCompatibility.FixInstructionOperands 实际会把 newobj/callvirt 改成 call，并把

[长期] 旧版本数据迁移（插件与备份）
================================================

需求（2026-11-06）：
换了新版/便携版之后「恢复备份」列表是空的，旧版本的插件和备份要自动找回来。

入口：ClassIsland/Helpers/LegacyDataMigrationHelper.cs，在插件扫描之前执行一次
（固定在 FileFolderService.CreateFolders() 之后、PluginService.ProcessPluginsInstall() 之前，
不能挪到插件扫描后面——迁移过来的插件要能在本次启动被扫到）。

定位旧版本（三类来源合并）
- 启动文件夹 %APPDATA%\...\Startup\*.lnk（WScript.Shell 读 TargetPath）；
- 注册表 HKCU / HKLM 的 Software\Microsoft\Windows\CurrentVersion\Run（含 32 位视图）；
- exe 相邻两级目录、%AppData%\ClassIsland\Data、%LocalAppData%。

[长期] 插件可选依赖按需下载
================================================

需求（2026-11-06）：
OpenCvSharp4、DlibDotNet 打进安装包会多 136MB，绝大多数人用不到，改成首次使用时下载。

实现：ClassIsland/Services/PluginDependencyService.cs（新增）
- 内置可选依赖清单（程序集名 → NuGet 包 + 需要抽取的文件），加新依赖只需添一条。
- 缓存目录 <数据目录>\PluginDependencies，托管库与原生库平铺同层。
- Ensure() 首次调用同步下载 nupkg，只抽取清单里的文件，不整包解压；
  下载源 api.nuget.org/v3-flatcontainer，失败回退 www.nuget.org/api/v2/package。
- 下载失败记 10 分钟冷却，避免每次解析都卡在同一个下载上。
- Prefetch() 在插件加载时后台读插件 dll 的 AssemblyRef，命中清单的提前下好。

接入
- ClassIsland/PluginLoadContext.cs：Load 增加缓存命中直接 LoadFromAssemblyPath、未命中调 Ensure()；
  LoadUnmanagedDll 增加缓存目录查找（OpenCvSharpExtern、DlibDotNetNative 等原生库）。
- ClassIsland/ClassIsland.csproj：移除 OpenCvSharp4 / OpenCvSharp4.runtime.win / DlibDotNet 三个引用。

实测：OpenCvSharp 3.4s / DlibDotNet 4.0s 下载，二次命中缓存 <100ms；
发布目录回到 290MB（不含 pdb），压缩后约 128MB。

异常收口（审计补充）
- Ensure() 由 AssemblyLoadContext.Load 的解析回调同步调用。原来只有 Download() 内部收异常，
  之后的解压、抽取文件、覆盖同层托管库一旦抛（磁盘满、文件被占用、无写权限），
  异常会直接冒到解析回调，整个插件被判「加载错误」。
  这跟「可选依赖不可用」是两件事：应该是这个功能用不了，而不是插件起不来。
  改为整段包 try/catch，捕获后写 FailedAt、返回 false，调用方按「依赖不可用」降级；
  顺带进 10 分钟冷却，避免每次解析都在同一处重复失败拖慢启动。

[长期] 原生库依赖自动检查与修复
================================================

需求（2026-11-17）：
把输出目录打包给别人后，在缺少 VC++ 运行库的机器上会直接崩溃（0x8007007E，miniaudio.dll
加载失败）。希望程序自己发现 runtimes 里原生库的依赖缺失，并自动从网上下载补齐。

检测
- 新增 Services/NativeDependencyService.cs：NativeDependencyProbe 负责扫描，
  PeImportReader 只读 PE 导入表，不加载目标 DLL，不触发 DllMain。
- 扫描范围：deps.json 里当前 RID 的 native 资产（runtimeTargets、assetType=native，
  过滤掉 .pdb 等非库文件）+ 应用根目录的 *.dll。
- 托管程序集也有导入表（mscoree.dll），按 CLR 运行时头（数据目录第 15 项）排除，
  否则每个托管 DLL 都会被误判成「缺 mscoree.dll」。同一个文件只打开一次，
  141 个文件整体约 20ms，启动路径无感。
- 依赖存在性：先看应用目录 / runtimes/<rid>/native 有没有同名文件，再按
  LoadLibraryExW(LOAD_LIBRARY_AS_DATAFILE) → LoadLibraryExW(0) 依次尝试。
- 同一个缺失模块常被多个原生库同时依赖（VCRUNTIME140.dll 等），按「问题类型 + 模块名」
  去重后只报一条。
- P/Invoke 显式写 ExactSpelling = true：LoadLibraryExW 名字本身已带 W 后缀，
  默认的 A/W 改写会先去找 LoadLibraryExWW，不能依赖 CLR 的精确名回退。
- 分类：VCRUNTIME140 / MSVCP140 / concrt140 / vccorlib140 / vcomp140 / ucrtbase /
  api-ms-win-crt-* → VisualCppRuntime；api-ms-win-* 与已知系统 DLL → SystemComponent；
  coreclr / hostfxr / hostpolicy / System.* → DotNetRuntime；其余 → ApplicationNative。

修复
- VisualCppRuntime：按进程架构下载 https://aka.ms/vs/17/release/vc_redist.{x64,x86,arm64}.exe，
  用 /install /passive /norestart 提权安装（会弹 UAC）；退出码 1638（已装更新版本）与
  3010（需重启）算成功。
- ApplicationNative：从 deps.json 反查所属 NuGet 包，下载
  https://api.nuget.org/v3-flatcontainer/{id}/{version}/{id}.{version}.nupkg，
  取出 runtimes/<rid>/native/xxx.dll 写回原位置。
- 下载先写 .tmp 再改名，避免半截文件被下次当成完整包复用。
- HttpClient 只在响应头阶段限时 30 秒，大文件下载不受影响；离线时不会让启动画面卡几分钟。

接入
- App.axaml.cs 在「提前初始化 IAudioService」之前调用 EnsureAsync，启动画面实时显示进度。
- AudioService 的 MiniAudioEngine 改为延迟创建：原来写在构造函数里（Task.Run(...).Result），
  缺运行库时整个应用在启动阶段就崩，连自动修复的机会都没有。失败结果不缓存，
  补装运行库后再次访问仍能恢复；Dispose 改成只释放已创建的引擎。
- Settings 新增 IsNativeDependencyAutoRepairEnabled（默认 true，可在变量调试页关闭）。
- 变量调试页新增「原生库依赖检查」卡片：开关、立即检查、自动修复、打开 runtimes 目录、

追加（2026-11-14）
--------
- 音频设备生命周期（审计补充）
  * TryInitializeDefaultPlaybackDeviceSafeAsync 初始化后立刻 Dispose 掉 RefCounted 的基础引用，
    租约一归还计数就归零，设备每次播放结束都被销毁，连续播报每句都要重新初始化。
    → 共享设备常驻，AudioService.Dispose 统一释放。
  * AudioEngine.PlaybackDevices 是初始化快照，插拔耳机后永远读不到新设备。
    → 每次取设备前按 2 秒节流调用 UpdateDevicesInfo()。
  * PlayAudioAsync 的 CancellationToken.Register 未注销，每播一段就在请求的 CTS 上多挂
    一个回调（连同 tcs/player 无法回收）。→ using 注销。

  把已取消的内容再念一遍。→ 先判 IsCancellationRequested 再报告失败。
- EdgeTTS 缓存非原子写：中断会留下半截 mp3，File.Exists 命中后永远播放损坏文件。
  → 写 .tmp 再 Move；回调只处理第一次。
- GPT-SoVITS 每次朗读 new HttpClient（端口耗尽 / TIME_WAIT），缓存也不是原子写。
  → 静态复用 HttpClient + 每请求 HttpRequestMessage 设置头；缓存 .tmp 原子替换；

  ObjectDisposedException，补捕获。

补充（2026-11-14 二次审计）
--------
- NotificationWorkerService.PlayingRequests 的遍历与增删不在同一线程：主计时器遍历它刷新
  进度，处理器的增删可能从后台线程的续体恢复。→ 加锁 + 遍历前取快照，
  避免「集合已修改」打掉整个定时器回调。
- 票据取消兜底：取消时请求仍是 Playing 说明还有 processor 在跑，正常情况下它的 finally
  会给宿主完成信号；但「遮罩正常结束、正文因时长为 0 被跳过」没有任何 processor 收尾，
  宿主会一直等下去。→ 注册取消回调时挂一个 1.5 秒延迟兜底，到点强制放行。

补充（子代理审计：取消后朗读与音频设备切换）
- NotificationWorkerService 取消路径的 finally 只 CancelAsync 音效 CTS，没清 SpeechService 队列；
  音效停了但已入队语音继续念完。→ 在取消收尾里 ClearSpeechQueue()，用 try/catch 隔离
  清理异常，保证后面的 cancellationCompletedSource.TrySetResult() 不被打断。
- AudioService 缓存命中路径读 PlaybackDevices 前没有 RefreshDevicesIfNeeded()，刷新只在
  Internal 路径；热插拔后新默认设备不进列表，IsSameDevice 误判同一设备，继续从旧设备出声。
  → 缓存命中路径也先 RefreshDevicesIfNeeded()（同锁可重入）。

补充（子代理审计第二批：设置首次落盘 / 插件下载卡死 / 预报卡片空引用）
- SettingsService 全新安装（没有 Settings.json）时，Settings 用的是字段初始化器里的默认实例，
  没走 else 分支也就没挂 PropertyChanged → SettingsChanged。本次运行里所有设置修改都不触发
  防抖保存，窗口大小、主题、语音开关等改动重启后全部丢失。→ 该分支补挂同一订阅。
- PluginMarketService.RequestDownloadPluginCore：构造下载器、读设置、绑定回调都在 try 之外，

  连 new DownloadProgress() 也做了兜底，避免它在登记下载任务时抛异常导致 Sentry 事务不结束。
- WeatherForecastNotificationProvider.BuildDays 是 fork 新增的 7 天预报卡片，只对

  → Info 与元素都判空，缺数据的那天退化成空温度区间。
- WeatherService 预警元素兜底（集合兜住了但元素字段没兜）：
  alerts 里出现 null 元素或 title/type/detail/images 为 null、images 缺 icon 键时，
  Title.Contains、GroupBy(...).ToDictionary（null key）、Images["icon"] 会连环抛异常，

补充（2026-11-14 二次审计：设置落盘与插件下载）
--------
- SettingsService 的 400ms 防抖把序列化挪到了线程池 Timer 回调，而 Settings 上有大量
  ObservableDictionary / ObservableCollection。UI 线程在这 400ms 窗口里增删排序这些集合时，
  后台枚举会抛「集合已修改」，这一次保存被吞掉；_pendingSaveNote 已清空，后面没有新的属性
  变更就不会再保存，用户改动静默丢失。→ 序列化回到 UI 线程（Dispatcher.Post），
  与集合修改天然串行，异常仍然整体兜住。
- ConfigureFileHelper：生成 .bak 的 File.Copy 与「读取 + 解析」共用一个 try。
  磁盘满 / .bak 被占用时配置其实已经读成功，却被当成损坏：写 .corrupt、再退回旧备份、
  用旧备份覆盖用户当前配置。→ 只把读取与解析放进 try，备份失败只记日志。
- PluginMarketService.RequestDownloadPlugin 是 async void，try 从方法中段才开始：
  解析市场项、启动 Sentry 事务、构造下载器（downloadUrl 为空时 DownloadBuilder 直接抛
  ArgumentNullException）都可能让异常直接杀进程。→ 方法体拆成 async Task，外层统一兜底。
- 下载完成回调前段（停表、Sentry 记速、错误分支）在 try 之外，而 Downloader 会把回调里的
  异常静默吞掉：异常一发生 downloadError 就不会被写入，随后把「下载失败 / 安装包根本没落盘」
  宣告成成功，提示用户重启，重启后插件并不存在。→ 整个回调包进 try；await 之后额外校验
  .cipx 确实存在。
- 暂停/推送提醒的公开入口不在 UI 线程时统一 marshal：ShowNotification / ShowChainedNotifications /
  CancelAllNotifications / Register(Unregister)NotificationConsumer 都可能被插件从后台线程调用。

[长期] 设置窗口关闭保存容错
================================================

运行反馈修复（2026-11-23）
- 现象：「部分情况下关掉应用设置页面会直接把整个主程序关掉」，一天可触发三次。
- 根因：ShutdownMode 是 OnExplicitShutdown，关设置窗口本身不会退出应用；真正的退出来自全局
  未处理异常处理器——默认教学安全模式 CriticalSafeModeMethod=0 会对任何未处理异常执行 Stop()。
  SettingsWindowNew.ViewBase_OnClosed 关闭窗口时保存设置/组件/自动化配置，三处调用此前没有任何
  异常保护，任一处因文件占用/磁盘写入失败/服务已释放而抛异常，都会冒泡到全局处理器进而退出主程序。
  与昨日提交（024eb3d0）无因果关系：该提交改的 6 个文件都不在设置窗口关闭链或退出链上；属于
  重新编译后暴露的偶发竞态。
- 处理：把三处保存各自用 try-catch 隔离（TrySaveOnClose），单项失败只记日志、不影响其它项和
  ReleaseResources()，异常绝不冒泡到全局退出链。
- 涉及文件：Views/SettingsWindowNew.axaml.cs。
